# Internationalisation (i18n)

Vita ERP supports 14 languages across both the frontend and backend. Each layer handles a distinct responsibility.

---

## Overview

| Layer    | Tool        | Responsibility                                      |
|----------|-------------|-----------------------------------------------------|
| Frontend | `next-intl` | UI strings (labels, buttons, headings)              |
| Backend  | Django i18n | Validation errors, API messages, system strings     |

---

## Supported Languages

| Code (frontend) | Code (Django) | Language              |
|-----------------|---------------|-----------------------|
| `en`            | `en`          | English               |
| `zh`            | `zh-hans`     | Chinese (Simplified)  |
| `es`            | `es`          | Spanish               |
| `hi`            | `hi`          | Hindi                 |
| `ar`            | `ar`          | Arabic                |
| `fr`            | `fr`          | French                |
| `pt`            | `pt`          | Portuguese            |
| `ru`            | `ru`          | Russian               |
| `de`            | `de`          | German                |
| `ja`            | `ja`          | Japanese              |
| `ko`            | `ko`          | Korean                |
| `it`            | `it`          | Italian               |
| `tr`            | `tr`          | Turkish               |
| `id`            | `id`          | Indonesian            |

> **Note:** The frontend uses `zh`; Django uses `zh-hans`. Django's `LocaleMiddleware` handles the partial match automatically via the `Accept-Language` header.

## Frontend

Translations live in `frontend/messages/{locale}/{namespace}.json`.

**Namespaces:**
- `common.json` — shared strings (navigation, actions, status)
- `auth.json` — authentication-related strings
- `themeEditor.json` — theme editor UI (module labels, control labels, tooltips)
- `formConstructor.json` — form constructor UI (~190 keys: editor, viewer, field types, validation, conditions, calculations, settings)

**Adding a new namespace:**
1. Add the namespace name to `frontend/src/config/i18n.ts` → `namespaces` array
2. Create `{locale}/{namespace}.json` for all 14 languages
3. Use in a component via `useTranslations('namespace')`

**Adding a new language:**
1. Add the locale code to `frontend/src/config/i18n.ts` → `locales` array
2. Add the same code to `backend/config/settings/base.py` → `LANGUAGES`
3. Create message files under `frontend/messages/{new-locale}/`
4. Run `python manage.py makemessages -l {new-locale}` in `backend/`

## Backend

Django's `LocaleMiddleware` activates automatically. It selects the language based on (in priority order):

1. URL prefix (when using `i18n_patterns`)
2. Session key
3. `django-language` cookie
4. `Accept-Language` HTTP header ← used by the frontend/API clients
5. `LANGUAGE_CODE` fallback (`en-us`)

Translation files live in `backend/locale/`.

### Generating translation files

```bash
cd backend

# Generate .po files for all languages
uv run python manage.py makemessages --all

# Or for a specific language
uv run python manage.py makemessages -l ru

# Compile .po → .mo (required at runtime)
uv run python manage.py compilemessages
```

### Marking strings for translation

```python
from django.utils.translation import gettext_lazy as _

class MyModel(models.Model):
    name = models.CharField(max_length=255, verbose_name=_("Name"))

# In serializers / views
raise ValidationError(_("This value is required."))
```

### Model-level translations (dynamic content)

For translating database content (e.g., product names, category labels), use `django-modeltranslation`. This is **not set up yet** — it will be added when the first translatable models are defined.

---

## Keeping both layers in sync

The source of truth for supported languages is:

- **Frontend:** `frontend/src/config/i18n.ts` → `I18N.locales`
- **Backend:** `backend/config/settings/base.py` → `LANGUAGES`

When adding or removing a language, update **both** files.
